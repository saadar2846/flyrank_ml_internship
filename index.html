Which Content Signals Actually Predict Decline?

A ranking signal audit on 30,000 real, anonymized search-content pages — FlyRank ML Internship Capstone

Abstract: This study asks which observable content and search signals actually predict content decline, testing common assumptions (staleness, position–CTR relationships) against 30,000 real anonymized content pages. I built a transparent baseline rule (stale content that is still visible in search → flag for review) and compared it against a Random Forest classifier under a client-grouped holdout split designed to prevent data leakage across clients. The model substantially outperformed the baseline at the top of the ranking — Precision@20 improved from 0.55 to 0.85 — though the improvement narrowed at Precision@50 (0.58 to 0.68), suggesting the model's advantage is strongest for its highest-confidence candidates. This is decision-support evidence for content review prioritization, not a causal claim about what makes pages decline.

Introduction / Problem Statement

Content teams routinely rely on intuition to decide what to review first — "older pages need refreshing," "better search position always means better click-through rate." This project asks whether those assumptions hold up against real data, and whether a learned model can prioritize review candidates more reliably than a hand-written rule.

Decision this supports: which signals a content strategist should weight when deciding what to fix on underperforming pages, replacing intuition with evidence.

Action: a strategist reprioritizes their content review checklist based on the ranked queue and reason codes this project produces.

Cost of a wrong call: wasted editorial time on signals that turn out to be noise, or — more seriously — mistaking a correlation for a cause and making a recommendation the data can't actually support.

Data

  • Release used: starter anonymized slice (data/raw/content_refresh_anonymized.csv) for development and final results; the warehouse release (FlyRank/internship-warehouse, build flyrank_pseudonymized_warehouse_release_v20260703) was explored separately for the full data contract exercise.
  • Tables: fact_content_daily_performance joined to dim_content on content_hash_id (warehouse); single flat CSV for the starter slice.
  • Scope: 30,000 content pages, filtered to impressions_90d > 0 and content_age_days >= 90.
  • Excluded, and why: all FlyRank product decision fields (health_score, priority_score, action_type, refresh flags) — these are not present in the release at all. This is a deliberate boundary: the goal is to discover signal from observable evidence, not to reconstruct and copy the product's own existing decisions.
  • No client names, domains, raw URLs, or private queries appear anywhere in this dataset or in this paper — all identifiers are pseudonymized.

Methodology

  • Task type: classification, used diagnostically for a signal audit — not as a production prediction system. The point is to learn which signals carry real information, not to ship a black-box predictor.
  • Label / proxy: is_declining_label = (trend_direction == "down") — a current-window proxy calculated from the present state of a page, not a validated future outcome. This is stated as a limitation, not smoothed over.
  • Features: content_age_days, days_since_last_update, impressions_90d, avg_position, ctr, word_count, sessions_90d, engagement_rate — all observable at decision time, none derived from the label.
  • Baseline: a transparent hand-written rule — a page is flagged if it is both stale (updated 180+ days ago) and still visible (500+ impressions in the last 90 days). Single reason code: stale_visible_page.
  • Model: a Random Forest classifier, chosen because it can capture interactions between signals (e.g. staleness only mattering when combined with visibility) that a single fixed threshold cannot express.
  • Validation design: a client-grouped train/test split (GroupShuffleSplit on client_id), not a plain random split — this prevents pages from the same client appearing in both train and test, which would let the model memorize client-specific quirks instead of learning transferable signal.
  • Leakage checks: every feature was confirmed observable at decision time; no FlyRank product flags were used; a deliberate-leak experiment (adding a label-derived column, watching the score jump toward-perfect, then removing it) confirmed the modeling pipeline is leakage-aware.

Client-grouped holdout split (20% of clients held out entirely); results from a 30,000-row anonymized starter slice. The baseline's ROC AUC (0.498, essentially at chance) looks alarming next to its Precision@20 (0.55, clearly above the ~0.54 base decline rate) until you consider why: a rule that only outputs three discrete score levels (0, 0.5, 1) can't form a smooth ranking curve, which limits how a full-threshold metric like ROC AUC can reward it. Precision@k is the more meaningful comparison for this ranked-review use case, since that's how the queue is actually consumed.

Notably, the model's Precision@20 (0.85) exceeds its Precision@50 (0.68) — confidence narrows as the review queue gets longer. The model's strongest signal is concentrated in its most-confident top predictions, not spread evenly across the top 50.

Limitations & Honest Framing

  • The label is a current-window proxy, not a confirmed future outcome.
  • This is observational data only — nothing here proves causation. A high score means "review this page first," not "refreshing it will fix it."
  • Validated on a 30,000-row anonymized starter slice, not the full ~79-million-row warehouse.
  • No claims are made about Google's ranking algorithm, and no claim is made that a content refresh causes recovery — neither is supported by this data.
  • All claims in this paper use observed, measured, directional, and decision-support language.

Ranked Recommendations

The model's output is turned into an action queue using reason codes, not a bare score:

  • model_decline_risk (model probability ≥ 0.65) or stale_visible_page (stale + visible under the baseline rule) → review for refresh
  • low_ctr_visible_page (visible, well-positioned, but low click-through rate) → review metadata / snippet
  • everything else → monitor only

Out of 30,000 pages, 14,893 were flagged for review under this scoring. Human review is required before any action is taken — this queue prioritizes attention, it does not authorize automatic edits, unpublishing, or any client-facing change. It should never be used to auto-publish changes, auto-prune pages, or make causal claims about why a page declined.
